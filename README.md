# Heat-safe shift planner (name TBD)

A Telegram bot that tells a construction-site supervisor which hours tomorrow are safe for outdoor work in extreme heat, and gives the crew the same plan as a Hindi voice note.

Entry for the WeMakeDevs x AWS environmental hackathon, Heat and Water track.

## The problem

Outdoor workers in Rajasthan keep working through dangerous afternoon heat because nobody turns the weather forecast into a shift decision. Heat forecasts exist; site-level instructions don't.

## Who it is for

- **The site supervisor.** One supervisor sets shift timing for a whole crew. They share the site's location once and get an hour-by-hour plan every morning.
- **The workers.** They get the plan as a short Hindi voice note, forwarded by the supervisor. No app, no reading.

## How it works

1. The supervisor sends a message or location to the Telegram bot.
2. Telegram posts the update to API Gateway, which triggers the `webhook` Lambda. It checks Telegram's secret header, saves setup state, invokes `planner` asynchronously and returns straight away.
3. `planner` runs a Strands agent on Amazon Bedrock. The agent fetches the hourly forecast from Open-Meteo and passes it to the risk engine.
4. The risk engine (`src/risk.py`) is plain, tested Python: NWS heat index plus IMD air-temperature cut-offs give each hour one of five bands. **The model never decides a band, a temperature or a time; it only words what the engine returns.** A guard checks every number in the model's text against the engine output and falls back to a template if any number was invented.
5. The plan goes back to Telegram as text. On request, Amazon Polly turns it into a Hindi voice note.
6. On dangerous days the plan ends with a fixed, human-reviewed heat-stroke warning that is never generated by the model.

## AWS services and open source

| Service | Used for |
|---|---|
| Strands Agents SDK (AWS open source) | Agent framework and tool calling |
| AWS SAM CLI (AWS open source) | Infrastructure as code, build and deploy |
| AWS Lambda | `webhook` and `planner` functions |
| Amazon API Gateway (HTTP API) | `POST /telegram` webhook endpoint |
| Amazon Bedrock | Claude Haiku, writes the plan text |
| Amazon Polly | Hindi voice note (voice Kajal, neural) |
| Amazon DynamoDB | Sites, plans and cooling points |
| Amazon S3 | Generated voice notes |
| Amazon EventBridge Scheduler | Daily 06:00 IST plan |
| AWS Systems Manager Parameter Store | Telegram token and webhook secret |
| Amazon CloudWatch Logs | Logs |

## Setup

Prerequisites: Python 3.11+, AWS CLI v2, SAM CLI, Docker (the build runs in a container), an AWS account with Bedrock access to Claude Haiku in `us-east-1`, and a Telegram bot token from @BotFather.

```bash
pip install -r requirements.txt
pytest
```

Store the secrets (once):

```bash
aws ssm put-parameter --region us-east-1 --type SecureString --name /hackathon/telegram_token --value "<bot token>"
aws ssm put-parameter --region us-east-1 --type SecureString --name /hackathon/webhook_secret --value "<random string>"
```

Build and deploy:

```bash
sam build
sam deploy --parameter-overrides BedrockModelId=<Claude Haiku model or inference profile ID>
```

Point Telegram at the deployed API, using the `WebhookUrl` stack output:

```bash
AWS_DEFAULT_REGION=us-east-1 python scripts/set_webhook.py <WebhookUrl>
```

Load the cooling points, using the `CoolingTable` stack output:

```bash
AWS_DEFAULT_REGION=us-east-1 COOLING_TABLE=<CoolingTable> python scripts/seed_cooling_points.py
```

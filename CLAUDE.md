## The problem and our user

Outdoor workers in Rajasthan keep working through dangerous afternoon heat because nobody turns the weather forecast into a shift decision. Heat forecasts exist; site-level instructions don't.

**Primary user: the site supervisor or contractor.** One supervisor sets shift timing for 20 to 50 workers. A single worker can't stop at noon, but a supervisor can move the shift. Every screen and message is designed for this person.

**Secondary user: the workers.** Many prefer voice over text and use basic Android phones. They receive the plan as a short Hindi voice note that the supervisor forwards to the crew's WhatsApp group.

## What the product does

Four flows, listed in build priority. Flows 1 and 2 are the minimum shippable product.

### Flow 1: Supervisor setup (once per site)

1. Supervisor opens the Telegram bot and sends `/start`.
2. Picks a language: Hindi or English.
3. Shares the site location using Telegram's location button, then types a site name (for example, "Tonk Road site").
4. Enters shift hours (default 07:00 to 18:00) and answers one yes/no question: is the work mostly in direct sun?
5. Bot saves the site and immediately sends tomorrow's plan.

### Flow 2: Daily plan (core feature)

1. Triggered at 06:00 IST every day, or when the supervisor sends "plan".
2. System fetches the hourly forecast for the site.
3. The risk engine scores every shift hour into a band (see Heat risk engine).
4. The agent writes a short plan from those scores: safe hours, mandatory breaks, the stop-work window, water reminders and one reason line ("heat index 46°C at 14:00").
5. Bot sends the text plus an hour-by-hour colour strip, and a "Send to crew" button.

### Flow 3: Crew voice note

1. "Send to crew" converts the plan into a Hindi voice note of 20 to 30 seconds using Amazon Polly.
2. Bot sends the voice note to the supervisor, who forwards it to the crew's WhatsApp group. We do not integrate WhatsApp directly.

### Flow 4: Red-flag safety message (fixed text)

Whenever any hour is rated Danger or worse, the plan ends with a fixed, human-reviewed message: confusion, stopped sweating, fainting or very hot skin are signs of heat stroke; move the person to shade, cool them with water and call 108 immediately. This text is stored in `copy/hi.json` and `copy/en.json` and is never generated by the model.

### Demo-only: replay mode

The supervisor (or the demo script) can request a plan for a past date. The system uses historical weather for that date instead of the forecast. The video uses a real May 2025 heat day in Jaipur, because October weather will not show the problem.

## Heat risk engine

The risk engine is plain, deterministic Python in `src/risk.py`. The AI model never decides a band, a temperature or a time; it only explains what the engine returns. This is our main safety argument to the judges.

**Inputs per hour:** air temperature (°C) and relative humidity (%) from Open-Meteo, plus the site's `direct_sun` flag.

**Step 1: Heat index.** Use the US National Weather Service Rothfusz regression with its published adjustments (NOAA WPC). The formula works in °F, so convert in and out. Heat index assumes shade; direct sun can add up to about 8°C.

```python
def heat_index_c(temp_c: float, rh: float) -> float:
    """NWS heat index (Rothfusz + adjustments). Input/output in Celsius."""
    t = temp_c * 9 / 5 + 32
    hi = 0.5 * (t + 61.0 + (t - 68.0) * 1.2 + rh * 0.094)
    if hi >= 80:
        hi = (-42.379 + 2.04901523*t + 10.14333127*rh - 0.22475541*t*rh
              - 0.00683783*t*t - 0.05481717*rh*rh + 0.00122874*t*t*rh
              + 0.00085282*t*rh*rh - 0.00000199*t*t*rh*rh)
        if rh < 13 and 80 <= t <= 112:
            hi -= ((13 - rh) / 4) * ((17 - abs(t - 95)) / 17) ** 0.5
        elif rh > 85 and 80 <= t <= 87:
            hi += ((rh - 85) / 10) * ((87 - t) / 5)
    return (hi - 32) * 5 / 9
```

**Step 2: Band.** Rate the hour on both columns below and take the higher band. Both are needed: Rajasthan's pre-monsoon heat is very dry, and in dry air the heat index can read below the air temperature.

| Band | Heat index (°C) | Air temperature (°C) | Action shown to supervisor |
|---|---|---|---|
| `SAFE` | below 27 | below 40 | Normal work, regular water |
| `CAUTION` | 27 to below 32 | 40 to below 42 | Normal work, water every 15 to 20 minutes |
| `EXTREME_CAUTION` | 32 to below 39 | 42 to below 45 | Shade break every hour; move heaviest tasks to the morning |
| `DANGER` | 39 to below 52 | 45 to below 47 | Light tasks only, long shade breaks, buddy checks |
| `EXTREME_DANGER` | 52 and above | 47 and above | Stop outdoor work |

Heat-index bands follow the NWS four-tier scale. The 40, 45 and 47°C air-temperature cut-offs follow IMD's heatwave criteria for the plains. The 42°C cut-off and the action text are our product decisions; we say so in the video.

**Step 3: Adjustments and outputs.**

- If `direct_sun` is true, raise every hour by one band (capped at `EXTREME_DANGER`).
- `stop_window` = the longest continuous run of `DANGER` or worse hours inside the shift, or none.
- Return, per hour: `hour`, `temp_c`, `rh`, `heat_index_c` (1 decimal), `band`. Also return `stop_window` and `max_band`.

**Tests** (`tests/test_risk.py`) must cover: heat index against at least five values read from the NWS heat index chart; every band boundary; the dry-air case where air temperature decides the band; the direct-sun bump; and stop-window detection.

## Architecture and tech stack

The whole system is Python 3.11, serverless, in one AWS region (`us-east-1` unless the team agrees otherwise), and deployed with a single SAM template.

### Request flow

1. The supervisor sends a message or location to the Telegram bot.
2. Telegram POSTs the update to API Gateway, which triggers the `webhook` Lambda.
3. `webhook` checks the `X-Telegram-Bot-Api-Secret-Token` header, saves any setup state, asynchronously invokes `planner`, and returns HTTP 200 within a second.
4. `planner` runs the Strands agent. The agent calls the forecast tool and the risk tool, and the cooling-point tool if needed.
5. The agent writes the plan text from tool output only. `planner` sends it to Telegram and, on request, generates the voice note with Polly.
6. EventBridge Scheduler triggers `planner` at 06:00 IST for every registered site.

### Stack

| Layer | Choice | Notes |
|---|---|---|
| Chat interface | Telegram Bot API, webhook mode | Free, no approval; built-in location sharing and voice notes |
| HTTP entry | Amazon API Gateway (HTTP API), `POST /telegram` | Single route |
| Compute | AWS Lambda: `webhook` and `planner` | `planner` is invoked async so Telegram never waits on the model |
| Agent framework | Strands Agents SDK (AWS open source, Python) | Tools are Python functions with the `@tool` decorator; pin the version |
| Model | Claude Haiku on Amazon Bedrock | Set the exact model ID via the `BEDROCK_MODEL_ID` env var; don't rely on Strands' default |
| Weather | Open-Meteo forecast API and archive API | Free, no key; hourly `temperature_2m` and `relative_humidity_2m`; archive for replay mode |
| Risk engine | `src/risk.py`, pure Python | No AWS or network calls; fully unit-tested |
| Voice | Amazon Polly, voice `Kajal`, neural engine, MP3 output | Bilingual Hindi and Indian English; use language code `hi-IN` so numbers are read in Hindi |
| Database | Amazon DynamoDB, on-demand | Three tables (see Data model) |
| File storage | Amazon S3 | Generated MP3 voice notes |
| Scheduler | Amazon EventBridge Scheduler | Daily 06:00 IST (`Asia/Kolkata` time zone) |
| Secrets | AWS Systems Manager Parameter Store (SecureString) | `/hackathon/telegram_token`, `/hackathon/webhook_secret` |
| Logs | Amazon CloudWatch Logs | Lambda default |
| Infrastructure as code | AWS SAM CLI (open source) | `sam build && sam deploy` |
| Local testing | pytest, `sam local invoke` | Risk and agent logic testable without deploying |

### Known gotchas

- Telegram `sendVoice` accepts OGG encoded with OPUS, MP3 or M4A. Polly's OGG output is Vorbis, so always request MP3 from Polly.
- Bedrock model access must be requested in the AWS console before the first call. Do this on day one.
- Lambda packages: Strands plus dependencies may be large. If the zip is too big, switch that function to a container image in SAM.
- Open-Meteo returns times in UTC unless you pass `timezone=Asia/Kolkata`; always pass it.

## Data model and interfaces

Three tables, two Lambdas, four agent tools. Don't add more without agreeing in the team chat first.

### DynamoDB tables

| Table | Keys | Attributes |
|---|---|---|
| `Sites` | PK `site_id` (string, UUID) | `chat_id`, `name`, `lat`, `lon`, `language` (`hi` or `en`), `shift_start` (`HH:MM`), `shift_end`, `direct_sun` (bool), `setup_step`, `created_at` |
| `Plans` | PK `site_id`, SK `date` (`YYYY-MM-DD`) | `hours` (list of objects from the risk engine), `stop_window`, `max_band`, `plan_text`, `audio_s3_key`, `source` (`forecast` or `replay`) |
| `CoolingPoints` | PK `city`, SK `point_id` | `name`, `lat`, `lon`, `type` (`water`, `shade` or `clinic`), `verified_by` |

### Lambda functions

| Function | Trigger | Responsibility |
|---|---|---|
| `webhook` | API Gateway `POST /telegram` | Validate secret header; run the setup conversation (state in `Sites.setup_step`); route "plan" and button presses; async-invoke `planner`; always return 200 |
| `planner` | Async invoke `{site_id, date, mode}`; EventBridge `{all_sites: true}` | Build the plan, save to `Plans`, send text to Telegram; on "Send to crew", generate and send the voice note |

### Agent tools (in `src/agent.py`, Strands `@tool`)

| Tool | Signature | Returns |
|---|---|---|
| `get_hourly_forecast` | `(lat: float, lon: float, date: str) -> list[dict]` | Hourly `temp_c` and `rh` for that local date; uses the archive API if the date is in the past |
| `score_hours` | `(hours: list[dict], direct_sun: bool, shift_start: str, shift_end: str) -> dict` | Output of `risk.py`: per-hour bands, `stop_window`, `max_band` |
| `nearest_cooling_points` | `(lat: float, lon: float, limit: int = 3) -> list[dict]` | Closest points from `CoolingPoints` by straight-line distance |
| `make_voice_note` | `(text: str, language: str) -> str` | Polly MP3 written to S3; returns the S3 key |

**Agent system prompt must enforce:**

1. Always call `score_hours` before writing a plan.
2. Never state a temperature, time or band that does not appear in tool output.
3. Supervisor message: at most 120 words. Voice script: at most 60 words.
4. Write in the site's language. Hindi must be simple and conversational, not formal.
5. Do not write the red-flag message; the code appends the fixed text whenever `max_band` is `DANGER` or worse.

**Output guard:** after the agent responds, `planner` checks that every number in the plan text appears in the `score_hours` output. If the check fails, `planner` sends a template-built plan instead of the agent's text.

## Repo conventions (added by C on 8 Oct, not part of the original brief)

These follow from how the SAM template packages the code. A and B: read before writing imports.

- **Lambda code root is `src/`.** Both functions are built from `src/`, so imports are flat: `import risk`, `import telegram_api`, `from handlers import planner`. Not `from src import risk`.
- **Handlers** are `handlers.webhook.handler` and `handlers.planner.handler`, each `def handler(event: dict, context: object) -> dict`. The files exist as placeholders so the stack deploys; B and A replace the bodies.
- **Tests** run from the repo root with `pytest`. `pytest.ini` puts `src/` on the import path, so tests also use `import risk`.
- **Copy files** ship inside the package: load them with `Path(__file__).parent / "copy" / "hi.json"` (from a module in `src/`).
- **Dependencies:** runtime pins live in `src/requirements.txt` (that is what SAM packages). The root `requirements.txt` includes it and adds pytest, so `pip install -r requirements.txt` still sets up everything.
- **`planner` is never retried** on failure (async retries are set to 0), so a crash cannot send the same plan twice. Log the error and move on.
- **Looking up a site by `chat_id`:** `Sites` is keyed on `site_id` only. `webhook` has permission to `Scan`; that is fine at demo scale. Ask C if you want an index instead.
